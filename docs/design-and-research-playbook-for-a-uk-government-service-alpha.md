A **repeatable set of design and research activities, tasks and outputs that an experienced multidisciplinary team can work through, using AI as a design partner throughout.**

This is not a checklist of things designers should produce. It's a process that helps designers make good decisions, investigate uncertainty, test ideas and build evidence.

For a new government service, structure the alpha around one central question:

**Can we demonstrate, through research and prototyping, that we have a viable service approach that meets users' needs and can be delivered within government constraints?**

Alpha is not primarily about designing the finished service. It is about reducing uncertainty before committing to a particular solution.

Organise the work into eight workstreams:

1. Understand the problem and the evidence.
2. Understand users and their needs.
3. Explore the end-to-end service.
4. Explore and test service concepts.
5. Design and test interactions.
6. Investigate accessibility and assisted digital.
7. Explore operational and organisational implications.
8. Consolidate evidence and make recommendations for beta.

## **1. The detailed alpha task list**

How to turn those eight workstreams into actual tasks that a service designer, interaction designer, content designer or user researcher can undertake.

### **Workstream 1 — Understand the problem and existing evidence**

**Objective:** Establish what the team knows, what it doesn't know, and what needs investigating.

| ID   | Task                                                              | Expected output                    |
| ---- | ----------------------------------------------------------------- | ---------------------------------- |
| 1.1  | Review the discovery findings and recommendations                 | Discovery evidence summary         |
| 1.2  | Review existing user research, reports and service data           | Research and evidence library      |
| 1.3  | Identify gaps, contradictions and weaknesses in existing evidence | Evidence gaps                      |
| 1.4  | Review the policy intent and legislative requirements             | Policy and legislative constraints |
| 1.5  | Understand the current service and administrative process         | As-is service map                  |
| 1.6  | Identify existing digital and non-digital channels                | Channel map                        |
| 1.7  | Identify the biggest problems and opportunities                   | Problem statements                 |
| 1.8  | Identify assumptions that the team is making                      | Assumptions register               |
| 1.9  | Identify the biggest risks to successful service delivery         | Initial risk register              |
| 1.10 | Agree what the alpha needs to learn                               | Alpha learning objectives          |

**How AI can help:**

- Analyse discovery reports and research documents.
- Extract user needs, pain points and opportunities.
- Identify contradictions between research findings.
- Summarise policy and operational constraints.
- Draft current-state service maps.
- Identify assumptions that have not been evidenced.
- Generate questions the team should investigate.

**Important:** AI-generated research findings must always be traced back to actual evidence. AI should not invent user needs or treat stakeholder opinions as user research.

### **Workstream 2 — Understand users and their needs**

**Objective:** Build a sufficiently detailed understanding of the people who will use, interact with or support the service.

| ID   | Task                                                              | Expected output                |
| ---- | ----------------------------------------------------------------- | ------------------------------ |
| 2.1  | Review existing user needs                                        | Prioritised user needs         |
| 2.2  | Identify and define user groups                                   | User group definitions         |
| 2.3  | Identify different user circumstances and contexts                | User context profiles          |
| 2.4  | Identify users with additional access needs                       | Inclusion considerations       |
| 2.5  | Map the different situations in which people need the service     | User scenarios                 |
| 2.6  | Understand what users are trying to achieve                       | User goals                     |
| 2.7  | Identify barriers that prevent users achieving their goals        | Barriers and pain points       |
| 2.8  | Identify users' existing behaviours and workarounds               | Behavioural insights           |
| 2.9  | Identify what users need to know, provide or do                   | User requirements              |
| 2.10 | Identify users' confidence, knowledge and capability requirements | User capability considerations |
| 2.11 | Identify unmet and emerging user needs                            | Opportunity areas              |
| 2.12 | Prioritise user needs using research evidence                     | Prioritised needs backlog      |

**How AI can help:**

- Cluster research observations into themes.
- Identify common behaviours across interview transcripts.
- Create draft user group descriptions.
- Generate scenarios for different user circumstances.
- Challenge whether a user need is genuinely a need or a proposed solution.
- Identify potentially excluded user groups.
- Create research questions to investigate gaps.
- Help prioritise needs based on evidence, frequency and impact.

**Research activity that must remain human-led:** Recruiting appropriate participants, conducting interviews, observing behaviour, understanding context and validating interpretations.

**Objective:** Understand the whole service experience, rather than just the digital transaction.

| ID   | Task                                                          | Expected output              |
| ---- | ------------------------------------------------------------- | ---------------------------- |
| 3.1  | Map the complete user journey from initial trigger to outcome | End-to-end user journey      |
| 3.2  | Identify how users discover and access the service            | Entry-point map              |
| 3.3  | Identify all user interactions and touchpoints                | Touchpoint inventory         |
| 3.4  | Map the information users need at each stage                  | Information requirements     |
| 3.5  | Map the documents and evidence users need                     | Evidence requirements        |
| 3.6  | Identify decision points and eligibility requirements         | Decision logic               |
| 3.7  | Map the back-office processes supporting the service          | Operational process map      |
| 3.8  | Identify staff, organisations and third parties involved      | Stakeholder and actor map    |
| 3.9  | Identify handovers between people, teams and organisations    | Handover map                 |
| 3.10 | Identify failure points, delays and unnecessary steps         | Service pain-point map       |
| 3.11 | Explore offline, telephone and assisted digital routes        | Alternative channel journeys |
| 3.12 | Identify what happens after the transaction is completed      | Post-transaction journey     |

**How AI can help:**

- Convert research into draft journey maps.
- Generate alternative journey scenarios.
- Identify missing steps and potential failure points.
- Create service blueprint drafts.
- Identify dependencies between teams and organisations.
- Challenge whether the service solves the whole user problem.
- Identify where users may need help or intervention.

This is particularly important in government. A service may look simple on the screen but involve complicated administrative processes behind it.

**Objective:** Explore different ways of solving the problem before committing to a particular design.

| ID   | Task                                                    | Expected output            |
| ---- | ------------------------------------------------------- | -------------------------- |
| 4.1  | Identify opportunities based on user needs              | Opportunity statements     |
| 4.2  | Generate different service approaches                   | Service concepts           |
| 4.3  | Explore digital and non-digital solutions               | Alternative service models |
| 4.4  | Challenge existing processes and policy assumptions     | Challenge log              |
| 4.5  | Explore different ways users could complete their tasks | Concept options            |

| 4.8  | Identify technical and organisational dependencies      | Dependency map             |
| 4.9  | Identify the assumptions behind each concept            | Concept hypotheses         |
| 4.10 | Select the most valuable concepts to prototype          | Prototype priorities       |

**How AI can help:**

- Generate multiple service concepts.
- Explore alternative ways of delivering a service.
- Challenge the team's preferred solution.

- Compare concepts against user needs.
- Identify potential unintended consequences.
- Create concept evaluation criteria.

Encourage designers to use AI to generate alternatives rather than simply asking it to improve the first idea.

## **2. How to organise the work into an alpha process**

Don't make the eight workstreams sequential. They should overlap, with research informing design and design generating new research questions.

For a typical 6–8 week alpha, use this structure as a starting point.

## **Suggested 8-week alpha workflow**

1. **Week 1 — Establish the evidence**

   Review discovery, understand users, map existing services, identify gaps and agree learning objectives.

   Output: Alpha research and design brief
2. **Week 2 — Understand the service**

   Develop user journeys, service maps, user scenarios and prioritised assumptions.

   Output: Current-state service model
3. **Week 3 — Explore solutions**

   Generate alternative service concepts, challenge assumptions and agree which concepts to test.

   Output: Concept options and hypotheses
4. **Week 4 — Prototype**

   Create low-fidelity prototypes, user flows and initial content. Identify high-risk interactions.

   Output: Testable prototypes
5. **Week 5 — Research and test**

   Conduct user research, usability testing and accessibility research. Test different approaches.

   Output: Research findings
6. **Week 6 — Iterate and investigate**

   Improve prototypes, explore operational processes, investigate technical and policy constraints.

   Output: Iterated designs and service blueprint
7. **Week 7 — Validate the approach**

   Test improved designs, validate important assumptions and assess remaining risks.

   Output: Validated service approach
8. **Week 8 — Recommend and prepare for beta**

   Consolidate evidence, recommend the way forward and create the beta design and research backlog.

   Output: Alpha recommendation and beta plan

Indicative structure, not a mandatory government delivery timetable. Some activities will run throughout the alpha.

The GOV.UK Service Manual describes alpha as a period for exploring different solutions and testing the riskiest assumptions. It specifically advises against building production-quality software or trying to prototype everything.

## **3. The important bit: how designers should work with AI**

Rather than designers having a list of generic prompts, create a **repeatable AI-assisted design workflow**.

Every task should follow roughly the same pattern:

## **The AI-assisted design task cycle**

1. **1. Give AI the context**

   Provide discovery findings, research, user needs, policy documents, existing service information and constraints.
2. **2. Ask AI to analyse**

   Identify themes, gaps, contradictions, opportunities and unanswered questions.
3. **3. Ask AI to generate**

   Create possible solutions, journeys, scenarios, hypotheses, flows or design options.
4. **4. Ask AI to challenge**

   Challenge assumptions, identify risks, consider excluded users and explore alternative approaches.
5. **5. Designer reviews and decides**

   The experienced designer evaluates the work, checks evidence, applies professional judgement and decides what to take forward.
6. **6. Research and validate**

   Take the work to real users, test it, gather evidence and document what was learned.
7. **7. Feed learning back into AI**

   Give AI the findings and ask it to help iterate the work and identify what needs investigating next.

The key principle is:

**AI generates possibilities and helps interrogate thinking. Designers make decisions. Research provides the evidence.**

### **Example: An AI-assisted task**

Imagine the designer is working on understanding user needs.

They could use the following prompt.

# Task: Analyse and prioritise user needs

## Role

Act as an experienced UK government service designer and user researcher.

## Context

I am working on a new government service in its alpha phase.

I will provide you with:

- Discovery research findings
- User interview transcripts
- Existing user needs
- Policy and service information
- Any relevant operational information

## Your task

1. Analyse the supplied evidence.
2. Identify the distinct user groups represented.
3. Identify the goals users are trying to achieve.
4. Identify their underlying needs, frustrations and barriers.
5. Identify common behaviours and workarounds.
6. Identify differences between user groups.
7. Identify unmet or poorly understood needs.
8. Identify contradictions or gaps in the evidence.
9. Identify assumptions that need further research.
10. Suggest a prioritisation of user needs.

## Output

For each proposed user need, provide:

- User group
- User need
- Supporting evidence
- Source reference
- Impact on the user
- Confidence in the finding
- Research gaps
- Suggested priority

## Important rules

- Do not invent user needs.
- Do not confuse a proposed solution with a user need.
- Do not treat stakeholder opinions as user research.
- Distinguish direct evidence from your interpretation.
- Clearly identify where there is insufficient evidence.
- Do not present assumptions as established facts.

Finish by recommending the five most important areas for further research during alpha.


This is the sort of repeatable interaction for every task in this alpha playbook.

## **4. Create a standard set of outputs and artefacts**

Make sure every task has an associated output. This gives the team something tangible to review and allows AI to work across the outputs as the alpha progresses.

Here is the core artefact library to establish.

| Artefact                   | Purpose                                       |
| -------------------------- | --------------------------------------------- |
| Discovery evidence summary | Establish the starting evidence               |
| User needs catalogue       | Maintain an evidence-based view of user needs |
| User group profiles        | Understand different user circumstances       |
| Assumptions register       | Identify what needs proving                   |
| Risk register              | Understand potential service risks            |
| Research plan              | Plan research and recruitment                 |
| Research repository        | Store findings and observations               |
| User scenarios             | Describe different situations and behaviours  |
| Current-state journey      | Understand the existing experience            |
| Future-state journey       | Describe the proposed experience              |
| Service blueprint          | Connect front-stage and back-stage activity   |
| Opportunity map            | Identify areas for improvement                |
| Concept catalogue          | Document alternative solutions                |
| Hypothesis backlog         | Track what needs testing                      |
| User flows                 | Describe interactions and decisions           |
| Prototype library          | Store testable design ideas                   |
| Usability findings         | Capture research evidence                     |
| Accessibility assessment   | Track inclusion and accessibility issues      |
| Content inventory          | Understand content requirements               |
| Decision log               | Record design decisions and rationale         |
| Alpha recommendation       | Explain what should move into beta            |
| Beta backlog               | Define the next phase of work                 |

Make these artefacts reusable and interconnected, rather than treating them as separate documents.

For example:

- A user need should link to the research evidence supporting it.
- A design decision should link to the user need it addresses.
- A prototype should link to the hypothesis it is testing.
- A research finding should link to the design changes it has informed.
- An unresolved risk should link to the work required to investigate it.

This creates an evidence trail from discovery through alpha and into beta.

## **5. Build a set of AI capabilities around the playbook**

Go one step further and create a library of AI-assisted design activities.

Group these into six capabilities:

**1. Research analyst**

Helps designers analyse evidence, identify themes, extract user needs, find contradictions and identify research gaps.

**2. Service mapping assistant**

Helps create user journeys, service blueprints, process maps, user scenarios and end-to-end service models.

**3. Design ideation partner**

Helps explore service concepts, alternative approaches, opportunities and possible solutions.

**4. Interaction design assistant**

Helps create user flows, wireframes, forms, interaction patterns, content and prototypes.

**5. Accessibility and inclusion reviewer**

Helps identify potential accessibility barriers, digital exclusion risks and alternative access requirements.

**6. Design assurance partner**

Challenges design decisions, checks alignment with user needs, identifies gaps and helps prepare assessment evidence.

These could become separate AI workflows, or simply different modes within one overarching alpha design assistant.

## **6. Make the playbook align with the GOV.UK Service Standard**

Explicitly map the work to the Service Standard so that the activities help teams produce evidence for their alpha assessment.

Some particularly important connections are:

| Service Standard                                      | Relevant alpha activities                            |
| ----------------------------------------------------- | ---------------------------------------------------- |
| 1. Understand users and their needs                   | Research, user groups, user needs                    |
| 2. Solve a whole problem for users                    | End-to-end journeys, service mapping                 |
| 3. Provide a joined-up experience across all channels | Service blueprints, channel mapping                  |
| 4. Make the service simple to use                     | Interaction design, prototyping, usability testing   |
| 5. Make sure everyone can use the service             | Accessibility, inclusion, assisted digital           |
| 6. Have a multidisciplinary team                      | Collaboration with policy, operations and technology |
| 7. Use agile ways of working                          | Iterative design and research                        |
| 8. Iterate and improve frequently                     | Testing, learning and design iteration               |

There are also important considerations around technology, security, privacy, performance and operational viability that the wider team needs to address.

## **7. This can be turned into a practical Alpha Design Toolkit**

There is an opportunity to create something more useful than a document containing tasks and prompts.

suggested structure for the finished product:

# **Alpha Design Toolkit**

An AI-assisted operating system for government service designers


**Part 1 — The process**

The end-to-end alpha process, phases, workstreams and recommended sequencing.

**Part 2 — The task library**

A detailed catalogue of design and research tasks, each with a purpose, instructions, inputs and outputs.

**Part 3 — The AI prompt library**

Tested prompts for completing each task, including instructions for evidence handling and critical review.

**Part 4 — The templates**

Reusable templates for user needs, research plans, journeys, hypotheses, service blueprints, design decisions and more.

**Part 5 — The quality framework**

Checks to ensure the work meets government design standards, is evidence-based and is ready for assessment.

**Part 6 — The alpha evidence pack**

A structured collection of the work and evidence needed to make a recommendation about moving into beta.

### **One important design principle**

Do not make this a rigid process where every task has to be completed.

Instead, every task should have:

- **Purpose:** Why are we doing this?
- **When to use it:** What circumstances make it relevant?
- **Inputs:** What information do we need?
- **Designer activity:** What should the designer actually do?
- **AI activity:** How can AI assist?
- **Research activity:** What needs validating with real people?
- **Outputs:** What should be produced?
- **Quality checks:** How do we know the work is good?
- **Dependencies:** What other tasks does this inform?

This makes it adaptable to different types of government service, rather than forcing every project through the same set of activities.

## **8. Where to take this next**

Experienced designers, such as leads, or under the oversight of leads, should trial v1 of this playbook, on real services.

Imporve this playbook based on that use.

Then look to develop this into a proper **Alpha Design and Research Task Framework**.

The next level of detail could be a master task catalogue, with perhaps 50–70 individual tasks. Each task would be written as an instruction that a designer can give to AI and then work through.

For example:

| Task                 | Designer asks AI to help them...                          |
| -------------------- | --------------------------------------------------------- |
| Analyse discovery    | Identify gaps and opportunities in the discovery evidence |
| Define user needs    | Extract and structure evidence-based user needs           |
| Map user journeys    | Build an end-to-end journey from research                 |
| Identify assumptions | Find and prioritise untested assumptions                  |
| Generate concepts    | Develop alternative service approaches                    |
| Create hypotheses    | Form testable hypotheses                                  |
| Design user flows    | Explore alternative interaction journeys                  |
| Create prototypes    | Generate prototype structures and content                 |
| Review accessibility | Identify potential accessibility issues                   |
| Analyse usability    | Synthesise research and recommend iterations              |
| Evaluate concepts    | Assess which service approach has the strongest evidence  |
| Prepare for beta     | Produce a prioritised design and research backlog         |

**The suggestion is that first build the task catalogue first, rather than starting with the prompts.** The tasks define the professional design process; the prompts are then designed to support each task.

That will create something much more valuable: a repeatable, AI-assisted way for experienced government designers to take a new service from discovery into a well-evidenced alpha and a confident beta recommendation.
